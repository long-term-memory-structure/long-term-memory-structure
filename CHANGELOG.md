# Changes

## Unreleased (0.2.2)

- **`ltms pin` holds no file whole.** Each file is read once, in chunks of 1 MiB through one buffer per run, and each chunk is hashed and written to the copy's temp file as it is read: the copy is made of the very bytes that were hashed, as before, and the memory a pin needs for a file's bytes no longer grows with the file's size, so a transcript of 2 GiB or more is pinned like any other. Until 0.2.1 a pin read each source whole into memory, and each copy too before writing over it: a transcript of 2 GiB or more failed every pin (`ERR_FS_FILE_TOO_LARGE`), and one larger than the memory a pin could use (a container's limit, or cron's) ended every pin at it. Measured on Linux (node 24.18) with sparse transcripts (a few lines around a hole of zeros), each pin under a memory limit of 256 MiB: transcripts of 1.5 and 4.25 GiB pinned new, then grown, each copy equal to its source by `sha256sum`, at a peak of 63 to 66 MiB (VmHWM); 0.2.1's pin of the 1.5 GiB one was killed at the limit, and it refused the 4.25 GiB one. A pin of a grown 100 MB transcript takes as long as in 0.2.1 (189 to 229 ms here, 0.2.1 198 to 206).
- **A pin killed after it read a file and before it renamed the copy's temp** (now written while the file is read) leaves that temp; the next pin keeps it beside the copy, with a `recovered` line, when no file of the pin holds its bytes: a duplicate of a version the source still holds, nothing lost.
- **`--rehash`'s cut back** (a copy holding its version, then bytes no pin wrote) reads the whole copy again before it writes, and writes nothing (`copy-changed`) when the copy is no longer exactly what it read first: bytes appended after the damage meanwhile were cut away by the first version of this change.
- **`--check`** counts as too large (`tooLarge`) only a source larger than a pin can address, 2^53 - 1 bytes; until 0.2.1, any source of 2 GiB or more.
- **Library:** `PinOptions` gains `chunkBytes` (the size of each read and write, 1 B to 64 MiB, default 1 MiB; the tests use small ones); `PinStep` gains `read` (after the source was read, hashed and written to the copy's temp, before the copy is read); `PinFailure.code` gains `copy-changed`. A pin also checks its lock before it makes a copy's temp, as before its rename.

### Known limits

- `PINS.log` is read whole at the start of each pin and each check, and a pin holds every path it walks: its memory grows by about 1 KiB per line of `PINS.log` (2.6 to 3.3 times the log's size) and by about 3 to 4 KiB per file. Measured: under a memory limit of 256 MiB, pins and checks were killed once the log passed about 250,000 lines; under 128 MiB, a project of 60,000 files. Such a pin is killed before it writes anything (a takeover of its dead lock aside).
- A pin killed at its start, after it took over a dead lock, still writes a `takeover` line, so the time of `PINS.log`'s last line can be recent while no pin has pinned a file: read `--check`'s counts (`missing`, `longer`).
- A temp left by a pin killed while it wrote a file that is not a `.jsonl` holds the first bytes of that file only, and the next pin keeps it as a version of the file, with a `recovered` line (as 0.2.1 did for a temp so cut; nothing lost).
- 0.2.1's other Known limits stand, but the first two (a transcript of 2 GiB or more; one larger than a memory limit), repaired here.

## 0.2.1 (2026-11-13)

- **The README opens with the design's first constraint, "Preserve potential indefinitely."**, for both its readers, people and agents evaluating the package; then the five facts the design answers (the record is on disk; it is deleted after `cleanupPeriodDays`; it is far larger than a context window; a wrong recollection becomes a wrong action; one agent, one user, one machine), the architecture, and the **technical debt**: every way an adversarial reading of 0.2.0 found the opening false, each with its state in this release. The commands follow.
- **`ltms pin`: the seven ways in which an act of pin destroyed a record in 0.2.0 are repaired**, each found by that reading (three readers, each finding sent to a fourth that tried to refute it) and each with a test that fails on 0.2.0's code:
  - The sweep of temp files ran before `PINS.log` was read and removed every file named like one: a source so named (its only copy, once the source was gone), and a temp file a killed pin left holding the only copy of a version. Now a file a line names is a copy, and a temp file is removed only when a file of the pin (its copy, or a kept copy of it) holds its bytes, or, for a `.jsonl` temp cut inside a line, which holds no version, its source; any other is kept, with a `recovered` line.
  - Two pins at once (a lock removed by hand while its pin ran; a dead lock taken over by two pins; a pin in another PID namespace, which saw a live lock as dead) wrote over each other's versions. The lock now also names, where `/proc` gives them, the boot id and the PID namespace: a lock from an earlier boot is taken over at once; one held in another PID namespace on this host counts as running. Before each write and each line, a pin checks that the lock still holds what it wrote and that `PINS.log` is the file it read, at the length it knows, and stops before that write when they are not (`lock-lost`, `log-changed`).
  - A copy was written over unread: pin read the copy only for a rewrite. Now it reads every copy before writing over it; one that is not what the run believes gets a `recovered` line (naming the kept copy of the version its last line records, when the pin holds one) and is decided against again, so a rewrite keeps it. `--rehash`, which writes a damaged copy again from its source, first keeps what the copy held beside it, a file of its own with its own `recovered` line, unless it is a `.jsonl`'s bytes that do not end in a new line (no pin writes those). A grown copy is compared with the source's first bytes in parts, never held whole beside it. Measured, a first pin and five grown pins of a 100 MB transcript: 156 to 170 ms each and a 256 MB peak on 0.2.0's code; 179 to 192 ms and 258 MB now.
  - A source named like a kept copy that a line names is not pinned there (`kept-name`). A directory of the pin that cannot be listed is not written into (its files fail; when it is the pin directory itself, the run stops before any file). A path whose log line could not be read back under the platform's rules is not pinned (`name-not-allowed`: the library's `platform: 'win32'` on Linux, with a `:` in a path).
- **`ltms pin`: four ways in which pins stopped and nothing told the user.** A file whose modification time lies past a JavaScript Date's range threw at that file in every pin (it is now written in ISO 8601's expanded form, `+287014-...`). A transcript of 2 GiB or more fails every pin, as in 0.2.0 (`ERR_FS_FILE_TOO_LARGE`, before it is read), and `--check` now counts such sources (`tooLarge`), says so, and exits 1. `~/.claude` moved to another disk behind a symbolic link refused every pin (a root whose recorded path leads to the same directory is now the same root, and `--check` gives its `--rehash` command through the link). `--check` exited 0 while `PINS.log` had another name (a `cp -al` snapshot of the pin), which every pin refuses (it now exits 1).
- **`ltms search --cache`** (experimental, opt-in; also `LTMS_CACHE=1`): a sieve per transcript, kept in `$XDG_CACHE_HOME/ltms/sieves` (else `~/.cache/ltms/sieves`), answers a file without opening it when no turn of it can hold the query, and has no false negatives. It keeps no text, but tells whether a word or a run of up to three characters is in its file, so short text can be pieced back: keep the cache as private as the transcripts. A sieve is keyed on its file (device, inode, size, and modification and change times), the ltms version, the sieve's format, and the runtime that read the file (its versions, its locale, a digest of the search's own reading of a fixed text, and the runtime's ICU files). A file modified in the last five minutes gets none; sieves kept more than 30 days ago are removed; on Windows none is kept. Without `--cache`, nothing is written and the output is 0.2.0's. Measured over 3,256 transcripts (6.9 GB), nine queries, each printing the same with and without the sieves: a rare word took 97.6 s without them and 2.0 s with them; a word most files hold, 112.6 s and 112.9 s (a sieve answers only for a file that cannot hold the query); making the sieves, the first time, 278 s.
- **Library:** `PinLockHolder` gains `boot` and `pidns`; `PinBusy` gains `otherNamespace`; `PinStaleness` gains `tooLarge`; `PinFailure.code` gains `kept-name`, `name-not-allowed`, `lock-lost` and `log-changed`. The sieve's exports, experimental: `sieveTranscript`, `sieveMayHold`, `sieveResult`, `searchRuntime`, `SEARCH_SIEVE_FORMAT`, `SEARCH_SIEVE_ASCII_GRAMS`, `SearchSieve` and `SearchBloom` (docs/library.md).

### Known limits

- A transcript of 2 GiB or more is not pinned (every pin fails on it; `--check` says so). Pinning it needs a streamed read and write.
- A transcript larger than the memory a pin may use (a container's limit, or cron's) ends every pin at it, and the files after it in name order are not pinned meanwhile; `--check` counts them missing or longer (README, Technical debt).
- A lock left by a pin killed in another PID namespace counts as running: every pin waits for it and exits 1 until it is removed by hand; `--check` exits 1, naming it.
- A pin checks its lock before each write, but the check and the write are two acts: a pin paused between them, after its lock was removed by hand or a dead lock was taken over twice, while another pin writes the same copy, can still write over that version.
- 0.2.0's Known limit stands: pin's commands that name a relative path starting with `-` give it without `--`.

## 0.1.1 (2026-11-09)

- 0.1.0's four known limits, all of `ltms pin`: three are fixed, and the fourth is narrowed to the bytes that can only be damage; what remains of it is stated in the README's Limits.
- `ltms pin --rehash`: recovery no longer records a copy that does not hold its version when its source cannot be read: one whose source, pinned in that run, cannot be read (the run fails on that file: its failure line, `read`, with the error code; exit 1), and one whose source the run cannot reach because its walk cannot read a path on the way, a directory it cannot list or a path it cannot look at (a `walk` failure line naming that path; exit 1). The copy is left as it is; once the source can be read, the next `--rehash` writes the copy again from it, with a `recovered` line, and keeps nothing of it. 0.1.0 recorded the copy's bytes, and the `--rehash` command `--check` then gave kept them as the old copy of a rewrite, which `--check` reported at every check, with no command.
- `ltms pin --rehash`: a `.jsonl` copy that holds its version at its start followed by bytes with no new line, which no pin wrote (a pin copies a `.jsonl` up to a new line), is no longer recorded by recovery. The run writes it again from its source (a `recovered` line when the source still holds that version, `grown` when it has grown); against a source rewritten since, or one with no whole line, it first cuts the copy back to that version, which a rewrite then keeps. Those bytes are never recorded or kept, so `PINS.log` no longer says `rewritten` for that source when it did not change. A copy that holds its version followed by bytes a pin could have written (whole lines of a `.jsonl`, or bytes of a file copied whole) is recorded as before, since they can be a version that only the pin holds (a pin killed between the rename of a grown copy and its line).
- `ltms pin --check`: after a mismatch in the copy of a file where a pin of its project does not go (under `.git`, or under `memory/` directly under a project directory; a file pinned by its own path), the `--rehash` command names that file by its own path, beside the projects of the other copies; run as printed, it writes the copy back. 0.1.0 gave the project's command, which changed nothing, at every check.
- `ltms pin`: the pin's own scan of its directory enters `.git`. For a file pinned by its own path under a source's `.git/`, 0.1.0 read the copy as missing: each pin of it wrote it again with a `recovered` line, saying the copy was missing, and a pin after its source was rewritten wrote over the copy without keeping its old version.
- `ltms pin --check`, while `PINS.log` has another name (a hard link): no line says what a next pin would do (unlogged files, temp files, the lock, a line cut short, a lock that is not a regular file); the notice says once that every pin into the directory is refused until the other name is gone. Its `find` command, and the `ls -l` command of the notice on a lock that is not a regular file, quote the path as the CLI's commands do, so they run as printed for a path that holds a space, a `'` or a `"`.
- Library: `projectPinReaches(rel)` on the `./pin` entry: whether a pin of the project directory of `rel` walks to the file (the walk enters no `.git` directory and no `memory/` directly under a project directory). `ltms pin --check` asks it for its `--rehash` command; the walk and it share one rule.
- README: the recovery sentence names these cases and says "as whole lines, for a `.jsonl`", names a copy whose source the run cannot reach (a directory it cannot list, or a path it cannot look at), and says that a pin without `--rehash` records such a copy meanwhile; the `--check` paragraph names the own-path command, and that nothing is said of a next pin while `PINS.log` has another name; Limits name every door to damage kept as an old copy (a pin without `--rehash`, and a `--rehash` that does not pin that copy's source) and what `--rehash` still records (bytes a pin could have written after a version, and, of a `.jsonl`, bytes that hold a new line but do not end in one).
- README: the link to the synthetic transcript `test/fixtures/demo.jsonl` is at the release's tag, as the link to `docs/library.md` is: the README shows that fixture's output as of the release.

## 0.1.0 (2026-11-09)

- `ltms search <query> <path>...`: finds the turns that hold every word of a query, in the transcripts named and in every `.jsonl` under the directories named. It prints addresses, key paths and offsets, never the text. The coverage line comes first (what was searched, what was not, every count). Then come the files with a hit, newest session first, each with its matching turns: at most `--max` turns (20; `0` for all), after the first `--skip` (0). The coverage's `shown` counts the matching turns passed over (`skipped`) and printed (`turns`), and `left` those after the ones printed, so `skipped + turns + left = hits.turns`; `next` is the command that prints the next ones (`--skip` past those printed, with the same `--max`). Options: `--kind <list>` (default: all but meta and attachment), `--substring`, `--max`, `--skip`, `--count`, `--oldest`. Exit 0; 1 when a file or a directory could not be read, or was too large; 2 on a usage error.
- search's closing line, on stderr, counts the matching turns and the files that hold them, out of the files found. For `ltms search --max 3 test` on a demo project's 35 transcripts: `ltms search: 173 matching turns in 35 of 35 files (35 read, 0 failed); 3 shown, 170 left: --skip 3 shows the next 3.`
- search refuses with the reason and the next command: no path (it names the current directory's project folder, or says that the current directory no longer exists), an unknown kind, a query with no word, and the query and the paths in the wrong order: a path that does not exist and looks like a word, or a query that names an existing path (one with a `/`, or ending in `.jsonl`) when no path argument names one (the query was left out). When a path argument does name one, such a query is searched, with a notice that gives the command for the other reading. Every command a message gives puts `--` before a query or a path that starts with `-`, so it runs as given.
- search's notices go to stderr. A query holding Hebrew, Arabic, Korean or spaceless-script letters draws one with the `--substring` command. `--substring` draws one for every query, each term echoed, saying what it costs: it also finds words that only contain them, as `cat` finds `concatenate` (the coverage's `mode` row says so too). A Node without `Intl` cannot run the search, and says so (exit 2); skeleton, stats and pin do not need it.
- search: a hit's `field` names keys down to a tool's parameter (the first level of its input), a system record's own keys and an attachment object's own keys, each by the label rule. A key below them is data a tool or the model wrote, and prints `(withheld)` even when it passes the label rule; an array counts as a level. Where `field` holds `(withheld)`, the window command in the help and the README prints the keys at that place whose value leads, along the rest of `field`, to a string longer than `at`, so one can be put in; where `field` leads to no string, or to one no longer than `at`, it says so (`not a string here`, `at is past the end of this field`), never with an empty line or a stack trace. The `system` kind reads every string of a system record but its envelope, its `subtype` and its `level`, which are names from a fixed list.
- search, under a directory: symbolic links are not followed, and each directory is read once, known by its device and inode (a bind mount of a directory inside itself would have its files read twice; tested on Linux, in a user namespace and with a stubbed `stat`, not on macOS or Windows). One warning line counts the files with nothing to search, the symbolic links, the entries named `.jsonl` that are not regular files (a pipe, a socket), the directories met again, and the files with warnings of their own; it names up to four of the latter, each with its kinds (lines that could not be read, records on a parentUuid cycle, responses read from parent links), and ends with the command that shows them.

- `ltms pin <path>... --to <dir>` keeps copies of the transcripts that Claude Code's cleanup deletes (after `cleanupPeriodDays`, 30 days by default). The library is the new `./pin` entry (`pinPaths`, `checkPin`, `claudeConfigDir`, `isSweepShaped`).

A copy missing from the pin while its source has been rewritten cannot be kept, and a notice says that its version is lost.

For a `PINS.log` or a lock that is not a regular file, and for a `PINS.log` that cannot be read, the next command is `ls -l` on it (in `--check`'s refusal and pin's, `--check`'s notice on the lock, and a pin's closing line after the failure at the lock). While the pin directory is open to group or others, each run says so, with the `chmod 700` command, and says that whoever it lets write into it can replace pin's files.

### Known limits (to be fixed in 0.1.1)

- A copy damaged so that its size changed and that is no prefix of its source, found by `--rehash` while its source cannot be read, is recorded as it is. When the source can be read again, the `--rehash` command that `--check` gives keeps those damaged bytes as the old copy of a rewrite, and `--check` then reports that version at every check, with no command. The current copy is written from the source: nothing the source still holds is lost.
- A file pinned by its own path under a `.git/` directory or under `memory/subagents/`, whose copy is then damaged: `--check` gives a `--rehash` command that changes nothing, at every check. Pinning that file by its own path with `--rehash` (`ltms pin <the file> --to <dir> --root <root> --rehash`) writes it again. The source is not touched: nothing it holds is lost.
- While `PINS.log` has a second name (a hard link), `--check` still says what the next pin records or removes, though every pin into the directory is refused until that name is gone; and the `find -samefile` command in its notice is not quoted for a path that holds a `'`: with one, the shell rejects it; with two, it searches a path that does not exist. No pin writes meanwhile: nothing is lost.
- A copy that holds its version followed by other bytes, its source unchanged: `--rehash` records those bytes and keeps them as the old copy of a rewrite, so `PINS.log` says `rewritten` though the source never changed. The current copy is written again from the source, and `--check` then passes: nothing is lost.
